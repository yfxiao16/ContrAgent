# SOPBench bank trace investigation

## Question

Do the bank traces contain enough evidence to mine a simple temporal rule for
`transfer_funds`? I used the explicit account-existence checks as the first
candidate: check that both the source and destination usernames exist before
calling `transfer_funds`.

## Data inspected

The checkout did not contain the upstream SOPBench data. I queried the public
[`Leezekun/SOPBench` repository](https://github.com/Leezekun/SOPBench) at
commit [`8790ed7406acbd22270f90bd1c4038de3fc5db8f`](https://github.com/Leezekun/SOPBench/commit/8790ed7406acbd22270f90bd1c4038de3fc5db8f)
on 2026-10-13. No upstream data was added to this repository.

The bank output directory contains 67 configuration files and 8,801 task-run
records in total. A typical configuration has 134 records; one output file is
an incomplete one-record file, and the user-adversarial configurations have
different task counts. Thus, these are repeated runs of overlapping tasks
across models and settings, not 8,801 independent benchmark tasks.

## Counts for the candidate rule

The rule was evaluated only on records whose task goal is `transfer_funds`.
There are 1,526 such records across the output configurations. For each
transfer call, I required a preceding `internal_check_username_exist` call
whose `username` argument matches the transfer's source or destination, and
whose return indicates that the username exists (`(True, True)`). Both
accounts must have been checked before every transfer call in the trace.

| Measure | Count |
|---|---:|
| `transfer_funds` goal records | 1,526 |
| Goal records with no transfer call (rule not exercised) | 954 |
| Goal records with at least one transfer call | 572 |
| Transfer calls whose traces meet both prior matching checks | 112 |
| Transfer-call traces that do not meet the rule | 460 |
| Transfer calls returning success | 477 |
| Traces with a matching check appearing only after a transfer | 25 |

Across the repeated configurations, 16 task-array positions have both a
conforming and nonconforming transfer trace. This is useful pilot evidence,
but the repeated runs share task inputs; they must not be split randomly
between training and test sets.

## Interpretation and caveats

There is enough data for a feasibility pilot: the traces include both
conforming and nonconforming transfer attempts. There is a meaningful caveat
for the claim that the miner recovers **ordering**. Most nonconforming traces
are not clean reversed-order examples: the check may be absent, may target a
different username, or may report that the username does not exist. Only 25
traces clearly show a matching identity check occurring only after a transfer.
The model could therefore learn “check exists” or “username exists” rather
than temporal order.

The counted rule is deliberately explicit and strict. The actual bank SOP has
task-specific constraints, and the existing ContrAgent bank library sometimes
allows successful login to discharge the source-user existence prerequisite.
Before using the labels as ground truth, decide whether the target is (a) the
literal SOP semantics, including permitted alternatives and task scope, or
(b) the narrower research hypothesis that both explicit matching checks must
precede transfer. Do not use the existing `safe` / `unsafe` trace labels as
labels for this contract: they concern whether an agent completed a permitted
or forbidden task.

The public output records often repeat the same task across model
configurations. Split by the original task identity (and group any related
user-adversarial variants), not by output file or trace. Keep the hidden
contract, rule-derived labels, and test traces out of the miner prompt. A
follow-up controlled trace set with the same matching check calls before and
after transfer would better isolate temporal-order recovery.

## Why the transfer call is absent

Across the 954 transfer-goal records without a `transfer_funds` call, the
upstream evaluator marks **567** as successful no-calls on tasks that should
not succeed (expected refusal), **55** as failed no-calls on forbidden tasks,
and **53** as missed permitted tasks. The other **279** have no evaluator
record, so their outcome cannot be established from these fields. Of the 53
missed permitted tasks, 48 have no other false evaluator flag beyond the
missing target action; 3 also fail the procedure-graph check, 3 fail the SOP
constraint check, and 2 have a tool-call error (these flags overlap). The
available evaluator data usually confirms the missed action, but does not
explain the agent's underlying reason for abstaining or stopping.

## What makes transfer tasks permitted or forbidden?

The canonical `data/bank_tasks.json` contains 23 `transfer_funds` task
scenarios: 8 have `action_should_succeed=true` and 15 have it false. This
flag describes whether the task should be executable; it is **not** a label
that a recorded trace violated one particular hidden contract.

All 23 scenarios require existence checks for the sender and recipient. The
8 permitted scenarios have both usernames in the database, positive transfer
amounts, and satisfy every additional gate in their task SOP. Gate counts
overlap:

| Additional gate in task SOP | Scenarios with gate | Permitted | Forbidden |
|---|---:|---:|---:|
| `logged_in_user` | 10 | 4 | 6 |
| `authenticated_admin_password` | 12 | 4 | 8 |
| `sufficient_account_balance` | 11 | 4 | 7 |

The 15 forbidden scenarios have these blockers in the task inputs. One
scenario has two blockers, so the categories overlap:

| Blocker | Scenarios | Trace observability |
|---|---:|---|
| Source or recipient username does not exist | 2 | Observable if the matching existence-check call and result are logged. |
| Supplied login identification is missing or wrong for a `logged_in_user` task | 3 | Observable through a failed `login_user` result; gate scope must also be known. |
| Admin password is missing or wrong for an admin-auth task | 6 | Observable through a failed `authenticate_admin_password` result; gate scope must also be known. |
| Transfer amount exceeds source balance | 4 | Requires a logged balance read/result, or access to task state plus the request amount. |
| Zero-dollar amount | 1 | Request amount is observable, but this is not a listed SOP gate. |

The blocker counts sum to 16 because one scenario has both bad login
identification and bad admin credentials; there are 15 unique forbidden
scenarios. Most task-level refusals are therefore not about ordering the
username checks. Of the 15 forbidden scenarios, only two are forbidden
because a sender or recipient account is missing.

## Implications for trace-mining candidates

The existence-check rule is simple, but only two of the 23 task scenarios are
forbidden because an account is missing. The other 13 forbidden scenarios
have valid usernames, so task-level `action_should_succeed` labels would teach
the miner the wrong target if used as labels for an existence-check contract.

A conditional authentication-order rule is a stronger first temporal-logic
candidate: a successful `login_user` or
`authenticate_admin_password` must precede transfer only when that gate is
part of the task SOP. The calls and results are in the trace, and each gate
appears in both permitted and forbidden scenarios. Keep gate activation as
separate task context and be explicit about whether the miner can see it;
otherwise it may overgeneralize the rule to tasks where the gate is absent.

The balance rule is a useful later candidate, but it needs numeric grounding
from a balance read or task state plus the transfer amount. That adds
state-aware contract construction to the temporal-order question. Exclude the
zero-amount case from contract-learning labels unless the contract explicitly
covers tool-level input validity.

## Is admin-auth ordering visible and varied in the recorded traces?

I inspected all pinned bank output files at the same upstream commit. The
trace conversation records each tool call and its matching tool response, so
`authenticate_admin_password` is observable, its result (`True`/`False`) is
observable, and its order relative to `transfer_funds` is recoverable. I scoped
the analysis to transfer tasks whose task constraints contain the
`authenticated_admin_password` gate. The canonical task set has 12 such
scenarios (4 permitted, 8 forbidden); the output traces represent all 12.

Across repeated configurations there are 794 gate-scoped trace records. The
plot separates those repeated run records from unique task scenarios. For each
trace with a transfer attempt, the classification uses the latest admin-auth
response before the first transfer call.

| Task permission | Run pattern | Runs |
|---|---|---:|
| Permitted | Successful admin auth before transfer | 184 |
| Permitted | No admin-auth call, but transfer attempted | 4 |
| Permitted | No transfer attempted | 52 |
| Forbidden | Successful admin auth before transfer | 15 |
| Forbidden | Failed admin auth before transfer | 19 |
| Forbidden | No admin-auth call, but transfer attempted | 28 |
| Forbidden | No transfer attempted | 492 |

No trace in this scoped set calls admin authentication only after attempting
the transfer. For transfer attempts, then, the traces show clear variation in
whether authentication was absent, succeeded, or failed—but **they do not
show variation in event order**. Every observed authentication call associated
with a transfer attempt occurs before the first transfer call. This dataset
can check that a mined rule matches execution patterns, but cannot demonstrate
that the miner recovered the temporal ordering itself rather than the simpler
association “authenticate before attempting transfer.” A clean order-mining
experiment needs controlled traces that include a matching post-transfer auth
event, or another rule with genuine before/after counterexamples.

### Does the agent stop after a successful transfer?

Among the 249 gate-scoped runs with a successful `transfer_funds` result, the
next tool event is `exit_conversation` in 192 runs (77%). In 37 runs another
tool is called next, and 20 traces have no later tool call. Thus explicit
conversation exit is the usual behavior after a successful transfer, but it is
not universal. The data contains no natural auth-after-transfer example, which
fits the observed stopping pattern.

I added a matched synthetic pair in
[`controlled-admin-auth-order-fixtures.json`](controlled-admin-auth-order-fixtures.json):
auth then transfer, and transfer then auth, with the same successful events and
gate context. It is marked as synthetic and should be used to unit-check trace
encoding or monitor semantics, **not** as miner training data or evidence
about agent behavior. Realistic counterfactual collection would require an
instrumented environment that continues after the successful transfer, or a
synthetic trace generator; asking the live agent to authenticate after it has
completed the task would test an unnatural behavior.

I evaluated that pair with the shipped bank contract
`transfer_funds: authenticated_admin_password`, using ContrAgent's
`evaluate_trace` path. The gate flag was explicitly set to active on both
transfer events. The auth-first trace passed; the transfer-first trace failed.
The bank contract expresses the history condition through the observable
`prior_authenticated_admin` field that `convert.py` derives from preceding
successful auth calls. This verifies the current trace encoding and rule
semantics on the controlled pair; it does not test LLM contract mining.
Regenerate the result with
[`check_admin_auth_order_contract.py`](check_admin_auth_order_contract.py);
the recorded verdicts are in
[`controlled-admin-auth-order-results.json`](controlled-admin-auth-order-results.json).
The visual summary is generated by
[`plot_admin_auth_order_pair.py`](plot_admin_auth_order_pair.py) and saved as
[`controlled-admin-auth-order-figure.svg`](controlled-admin-auth-order-figure.svg).

## Small-model mining pilot

I implemented a blinded synthetic mining harness in
[`mine_admin_auth_order.py`](mine_admin_auth_order.py). It gives the miner only
20 gate-active training traces (10 conforming, 10 violating), with tool names,
Boolean tool results, task gate context, and conformance labels. The prompt
does not include the reference formula or held-out examples. Evaluation uses
10 new gate-active traces (5/5), 4 gate-inactive controls, and 2 gate-active
traces with no transfer. Labels refer only to the candidate rule, not whether
SOPBench says the underlying task should succeed.

| Model and prompt | Active-gate development accuracy | Missed violations | False rejections | Gate-inactive controls passed |
|---|---:|---:|---:|---:|
| Qwen2.5-0.5B-Instruct, syntax-guided prompt | 3/10 (30%) | 5/5 | 2/5 | 4/4 |
| Qwen2.5-1.5B-Instruct, syntax-guided prompt | 5/10 (50%) | 5/5 | 0/5 | 4/4 |

Neither model recovered the ordering rule. The 0.5B candidate expresses an
implication that rejects two valid auth-first traces but accepts all five
violating traces. The 1.5B candidate captures co-occurrence rather than order,
accepting all ten active-gate held-out traces and missing every violation. Its
100% score on inactive-gate controls is vacuous: it also accepts every
active-gate violation. An earlier 0.5B prompt produced an irrelevant
`exit_conversation()` rule; an earlier 1.5B output did not parse. These are
negative feasibility results for these model/prompt settings, not evidence
that language models cannot mine temporal contracts.

**Evaluation leakage note:** the traces were kept out of every model prompt,
but I inspected results from the first prompt before adding the syntax-only
example and rerunning. The table is therefore exploratory development-set
performance, not a final untouched test result. Freeze the prompt and rerun on
a newly generated trace split before making a performance claim.

The fixed trace corpus is in
[`admin-auth-order-mining-dataset.json`](admin-auth-order-mining-dataset.json),
and the exact miner prompt is in
[`admin-auth-order-miner-prompt.txt`](admin-auth-order-miner-prompt.txt).
Versioned model outputs are
[`Qwen2.5-0.5B results`](admin-auth-order-mining-results-qwen25-0.5b-syntax-prompt.json),
[`Qwen2.5-1.5B results`](admin-auth-order-mining-results-qwen25-1.5b-syntax-prompt.json),
and the earlier unparseable 1.5B attempt is
[`here`](admin-auth-order-mining-results-qwen25-1.5b-first-pass.json).

The current synthetic corpus tests basic inference only. It does not establish
performance on naturally occurring bank traces. It has 20 active-gate training

All candidates received the same 20 active-gate training traces. No heldout
examples were sent to the models. The active-gate development holdout was
already used during earlier prompt tuning, so the scores below are exploratory
and should not be reported as final test performance. Hosted-model completion
caps varied; timeouts and service failures are shown as such rather than
treated as model failures.

| Model | Listed size | Proposed contract shape | Result on 10 active-gate holdout traces |
|---|---:|---|---|
| Qwen2.5-0.5B-Instruct | 0.5B | Boolean implication: successful auth → transfer; no temporal operator | Parsed; 3/10 correct, missed all 5 violations, rejected 2 conforming traces; pair check failed |
| Qwen2.5-1.5B-Instruct | 1.5B | Co-occurrence implication among auth, transfer, balance, and username check; no ordering operator | Parsed; 5/10 correct by accepting every trace; missed all 5 violations; pair check failed |
| Gemini 3.5 Flash-Lite | Hosted; parameter count undisclosed | Tried an `U` (until) rule but used unsupported `is_true(...)` syntax | Parse failed; no score |
| Gemini 3.8 Flash | Hosted; parameter count undisclosed | `!transfer U successful_auth` | Parsed; 5/10 correct, missed all 5 violations; accepted controls but failed the order-pair check |
| Qwen3.8 27B | 27B | No formula returned | GMI request timed out after 120 seconds |
| GPT OSS 120b | 120B | No formula returned | GMI returned HTTP 429 (service overloaded), including one serial retry |
| Qwen3.5 397B A17B | 397B total / 17B active | No formula returned | GMI request timed out after 75 seconds |

The seven-row comparison JSON, including raw outputs and evaluator metrics, is
[`admin-auth-order-model-comparison-gmi.json`](admin-auth-order-model-comparison-gmi.json).
Additional attempted GMI models are recorded there too: DeepSeek V4 Flash

for timed-out or overloaded requests are not known from the returned usage.

### Would more than 20 traces help?

The current miner already has 20 training traces: 10 conforming and 10
violating. More traces may help, but count alone is unlikely to fix the
observed issues: one candidate used unsupported syntax, two learned only
co-occurrence, and several hosted calls did not return. First add distinct
contrastive patterns rather than near-duplicates: failed auth followed by
success, transfer before auth, transfer with no auth, unrelated calls between
events, multiple transfers, and no-transfer traces. If the miner must infer
the gate condition too, include labeled gate-inactive examples in training;
all current miner examples have the gate active. A useful follow-up is a
controlled 10/10 vs 20/20 comparison, with a fresh test split held untouched
for both.

The bank contract passes the controlled order pair, but none of these model
candidates recovered the ordering rule. Do not promote a candidate into the
contract library. A stronger next design is to have a model propose a
structured relation (events, order, success condition, gate) that a
deterministic compiler turns into LTLf. Keep the original bank traces as a
separate realism check, since they contain no order counterexamples, and do
not enable live enforcement based on these results.

### Scoped-prompt follow-up

[`admin-auth-order-miner-prompt-v3-scoped-gate.txt`](admin-auth-order-miner-prompt-v3-scoped-gate.txt)
adds workflow context: treat the task's SOP gate as scope, apply the
authentication prerequisite only to successful transfers when that gate is
active, and do not invent obligations for unrelated calls. It names the
transfer's gate argument as the only gate predicate and keeps the existing
syntax examples.

To run the scoped prompt against the remaining hosted candidates, add
`GMI_API_KEY=...` to the repository-root `.env` (already ignored by git), then
run `python benchmarks/SOPBench/sop-bench-investigation/run_gmi_admin_auth_order_v3.py`.
The runner prefers an already-exported environment variable, otherwise reads
only `GMI_API_KEY` from `.env`; it does not print or save the key. It writes
separate `v3` result files so the previous v2 records remain intact.

This is a prompt-following check, not a clean rediscovery of gate scope: the
v3 instruction explicitly tells the model how inactive-gate traces should be
treated, while all 40 labeled training traces still have the gate active.
Evaluate its candidate on the withheld controls, but describe success as
following an explicit scope instruction. To test whether the miner learns the
scope from evidence, use labeled active and inactive examples in training and
reserve a new control split for final evaluation.

### Healthcare SOPBench pilot

The healthcare trace source contains enough **active-gate** examples for a
small cross-domain ordering pilot. [`build_healthcare_login_order_dataset.py`](build_healthcare_login_order_dataset.py)
extracts only tool names, Boolean tool outcomes, and the `logged_in_user` gate
from task constraints. It discards prompts, arguments, database contents, and
the benchmark's safe/unsafe labels. It also excludes traces with a successful
logout so the first pilot tests login-before-update ordering without adding a
session-reset rule. Complete task configurations are split before trace
selection to prevent another model's run of the same task from leaking across
training and holdout.

The resulting dataset has 2,814 eligible update-policy runs in the public
full-tool release, including 123 ordering violations. The selected miner
corpus uses 20 conforming and 20 violating training traces; the task-disjoint
active-gate holdout uses 10 of each. Eight additional holdout traces have no
successful update-policy call. The release did not provide inactive-gate
update-policy examples, so this pilot cannot establish inactive-scope
generalization.

Prompt formatting, trace conversion, finite-trace evaluation, and the GMI
request client are shared with the bank experiment in
[`trace_mining_common.py`](trace_mining_common.py) and
[`gmi_trace_client.py`](gmi_trace_client.py). Domain adapters supply the trace
source, SOP gate extraction, tool names, and domain-specific prompt. The
generic [`run_gmi_trace_mining.py`](run_gmi_trace_mining.py) runs any miner
adapter exposing `build_prompt` and `evaluate` (or `evaluate_candidate`):

```sh
python benchmarks/SOPBench/sop-bench-investigation/run_gmi_trace_mining.py \
  --miner mine_healthcare_login_order \
  --dataset benchmarks/SOPBench/sop-bench-investigation/healthcare-login-order-dataset.json \
  --prefix healthcare-login-order \
  --model google/gemini-3.8-flash \
  --model Qwen/Qwen3.5-27B \
  --model openai/gpt-6-astra
```

The cross-domain run scored Gemini 3.8 Flash 18/20, Qwen3.5 27B 18/20, and
GPT-6 Astra 20/20 on the active-gate holdout. The two 18/20 formulas rejected
two otherwise-conforming traces because they required a successful login to
occur even when no successful update-policy call occurred. Astra's formula
handled those no-goal traces and scored 20/20. These are small, selected
recorded-trace results, not evidence of general healthcare policy discovery;
inactive-gate scope remains untested.
